# QA API Trainer

Веб-тренажёр для обучения QA тестированию API. Ключевая идея:
**эталонная спецификация + намеренно сломанный fake-сервер + клиент запросов**.
Отличие от Postman в том, что здесь есть «правильный ответ»: спека известна,
баги вшиты списком, поэтому тренажёр может проверять, нашёл ли студент
расхождение.

Это **не** клон интерфейса Postman. Интерфейс минимальный, вся ценность в
контенте — в багах и заданиях.

## Текущее состояние

**v0.1, v0.2, v0.3, v0.3c, v0.4, v0.4.1 и v0.4.2 закрыты.** Работает: спецификация в левой панели, конструктор
запроса, отправка в mock-сервер, просмотр ответа с подсветкой JSON, история
запросов с восстановлением по клику, кнопка сброса состояния сервера, форма
баг-репорта со сверкой по каталогу, счётчик «найдено N из 10», лента репортов
с вердиктами, подсказки по одной, проверка ответа по JSON Schema через ajv и
панель Tests с объектом `pm` и своим мини-`expect`, сохранение работы в
`localStorage`, переменные окружения с подстановкой `{{имя}}` и цепочки
запросов через `pm.environment.set`, список заданий и справка по интерфейсу,
визуальная иерархия интерфейса.

Осознанно отсутствует: коллекции, прогон коллекции целиком, режим экзамена,
сценарии кроме Users. Всё это — следующие версии, см. роадмап ниже.

Следующий шаг: **v0.5 — коллекции, прогон целиком, новые сценарии**. Это
три разные вещи, начинать надо с разбивки.

Ветка `main`, удалённый репозиторий —
[Punk-and-Babka/qa-api-trainer](https://github.com/Punk-and-Babka/qa-api-trainer),
публичный. Сайт публикуется на GitHub Pages при каждом push в `main`:
https://punk-and-babka.github.io/qa-api-trainer/

## Стек и жёсткие ограничения

- React + Vite, **чистый JavaScript, не TypeScript**.
- Обычный CSS. Без Tailwind, без UI-китов, без Material UI.
- Состояние — `useState`/`useReducer`. Без Redux, Zustand, react-query.
- Роутинга нет и на v0.1 не нужен.
- Зависимости проекта: `react`, `react-dom`, `vite`, `@vitejs/plugin-react`,
  `ajv` и `ajv-formats`. Подсветка JSON написана вручную
  (`src/components/JsonView.jsx`) вместо внешней библиотеки.
  `ajv` добавлен в v0.3a осознанно: полноценный валидатор JSON Schema — это не
  «полсотни строк своего кода», а самописное подмножество учило бы
  почти-стандарту. `ajv-formats` обязателен в нагрузку — без него ключевое
  слово `format` молча игнорируется. Цена: бандл вырос с 76 до 116 КБ gzip.
- **Любая новая npm-зависимость сначала предлагается и обосновывается, и
  ставится только после явного согласия.**

## Запуск

```
npm install
npm run dev
```

Открывается `http://127.0.0.1:5173/`.

**Важно: в `vite.config.js` намеренно прописан `host: '127.0.0.1'`.** По
умолчанию Vite слушает имя `localhost`, а Node начиная с 17 версии не сортирует
результаты резолва — на этой машине первым идёт `::1`. При этом IPv6-петля
здесь не работает (`ping ::1` даёт 100% потерь: VPN-клиент с TUN-адаптером
перехватывает IPv6-маршрут). Симптом был обманчивый: сервер поднимался и писал
«ready», но страница в браузере не открывалась. Эту строку не удалять.

Смежное: `netstat -p tcp` на Windows показывает **только IPv4**. Чтобы увидеть
IPv6-сокеты, нужен `netstat -p tcpv6` — иначе легко решить, что сервер вообще
не слушает.

## Коммиты в публичном репозитории

Репозиторий публичный, поэтому в новые коммиты не идут две вещи:

- **трейлер `Claude-Session:` со ссылкой на сессию** — он раскрывает
  идентификатор сессии Claude Code;
- **машинный email `Имя@ИМЯ-КОМПЬЮТЕРА`**, который Windows подставляет по
  умолчанию: он раскрывает имя учётной записи и имя компьютера.

Вместо машинного адреса локально для этого репозитория прописан
`user.email = Punk-and-Babka@users.noreply.github.com`. Настройка локальная,
а не глобальная: другие проекты на машине не затронуты.

История переписана не была — решение было чистить только будущее. В первых 23
коммитах трейлеры и машинный email остались. Важно понимать, почему
переписывание не сделали походя: `force-push` меняет хеши, но старые объекты
на GitHub остаются доступны по прямой ссылке на SHA, так что «стереть» их
можно только удалением и пересозданием репозитория.

## Публикация на GitHub Pages

Собирает и публикует `.github/workflows/pages.yml` при push в `main`; можно
запустить вручную из вкладки Actions. Приложение целиком клиентское, поэтому
публикуется обычная статика из `dist`.

**`base` в `vite.config.js` зависит от команды:** `/qa-api-trainer/` для
сборки и `/` для dev-сервера. Проектный сайт на Pages отдаётся из подкаталога
с именем репозитория, и без `base` Vite впишет в `index.html` абсолютные пути
вида `/assets/index-abc.js` — на Pages они укажут в корень домена, страница
откроется пустой, а в консоли будут 404 на скрипт и стили. Симптом обманчивый:
локально всё работает.

Значение прописано строкой, а не берётся из переменной окружения намеренно: на
этой машине Git Bash преобразует значения, похожие на POSIX-пути, в
Windows-пути, и в собранный HTML попал бы `C:/Program Files/Git/...`.

В workflow используется `npm ci`, а не `npm install`: ставятся ровно те версии,
что записаны в `package-lock.json`.

### Контракт mock-сервера

```js
// вход
{ method, path: "/users/1", query: { limit: "10" }, headers, body }
// выход
{ status: 200, headers: {...}, body: {...}, time: 43 }
```

`handle()` — **синхронная функция**. Задержку ответа изображает `setTimeout` в
`App.jsx` на то число миллисекунд, которое вернул сам сервер. Внутрь роутера
задержку не вносить: он должен оставаться вызываемым из проверки одной строкой
без `await`.

Неизвестный путь → 404 с телом `{ "error": "Not found" }`.

### Принципиальные решения

**Состояние сервера живёт в модуле, а не в React.** Fake-сервер обязан
переживать перерисовки компонентов. `resetState()` копирует каждую запись
из `SEED_USERS` через spread — иначе обработчики мутировали бы эталон и сброс
перестал бы работать.

**Спека и каталог багов — это данные.** `SpecPanel` обходит объект контракта и
не знает про конкретный сценарий: новый эндпоинт добавляется правкой одного
`users.contract.js`. То же для багов — в v0.2 `users.bugs.js` станет эталоном
для проверки баг-репортов.

**Само дефектное поведение остаётся кодом.** Декларативного движка, который
«портит» корректный ответ на лету, сознательно нет: часть багов (B6 — поле
молча не сохраняется, B8 — 200 с телом null) невыразима декларативно без языка
правил, который окажется больше всего сервера. Вернуться к этому решению можно
в v0.5, когда багов станет много.

**Баг опознаётся по паре «эндпоинт + тип дефекта», и уникальность пары —
явный инвариант каталога.** Свободный текст описания сверяется человеком, а не
машиной: он показывается рядом с эталонной формулировкой, но на счётчик не
влияет. Альтернативы (ручная отметка «совпало» студентом, подтверждение эталона
после автосверки) обсуждались и отклонены: счётчик должен что-то доказывать, а
не накручиваться. Слабое место такой сверки — она ломается молча, если два бага
дадут одну пару, поэтому `users.bugs.js` при импорте вызывает
`assertUniquePairs()` и падает с указанием конфликтующих id. Раньше уникальность
пар была случайным свойством данных, теперь это проверяемое требование.

**Логика сверки вынесена из React в `src/bug-check.js`.** `checkReport()`,
`endpointOptions()` и `foundBugIds()` — чистые функции над массивами: их видно
целиком, их можно прогнать из Node одной строкой и позже покрыть тестами, не
поднимая браузер.

**Список эндпоинтов для формы считается из контракта**, а не пишется руками:
новый эндпоинт появляется в спеке и в выпадающем поле одновременно. Пункт `*`
дописывается отдельно — он не эндпоинт, а способ сообщить о дефекте во всех
ответах сразу (B9, формат даты).

**Черновик формы баг-репорта живёт в самом компоненте** — сознательное
отступление от правила «App владеет всем». Правило появилось ради истории
запросов, где клик по элементу обязан перезаписать поля извне. Черновику это не
нужно: снаружи его никто не задаёт и не читает, наверх уходит только готовый
репорт. Поднимать такое состояние — четыре лишних props без выигрыша.

**Вердикт репорта считается в обработчике, а не внутри `setReports`.** Здесь,
в отличие от истории, обработчик выполняется синхронно по клику, и `reports` в
нём актуален — устаревшего снимка, из-за которого истории понадобилась
функциональная форма, не возникает. Внутрь updater'а нельзя класть и счётчик
`reportId`: React вправе вызвать функцию обновления дважды, она обязана быть
чистой. Сам append при этом всё равно сделан функциональной формой.

**Найденные баги не хранятся состоянием** — `foundBugIds(reports)` считается
при рендере из ленты репортов. Тот же принцип, что и с разобранным путём.

**Подсказки открываются по одной и только для ненайденных багов**, в порядке
каталога. Число открытых подсказок показано рядом со счётчиком: это честная
оценка результата, а не наказание — засчитывание от подсказки не зависит.

**Сброс состояния сервера не трогает прогресс.** Он касается только данных
сервера; найденные баги и лента репортов — результат работы студента.

**Схемы пишутся по спецификации, а не по фактическому поведению.** Иначе
проверка подтверждала бы баги вместо того, чтобы их ловить. Побочный эффект
намеренный: `additionalProperties: false` ловит `passwordHash` (B3),
`format: date-time` — дату без `T` (B9), `required` — отсутствие `role` в
списке (B10), а `type: object` — тело `null` вместо 404 (B8). Поэтому проверка
запускается кнопкой, а не автоматически: сначала студент смотрит глазами,
потом сверяется машиной. Это методический выбор, а не техническое ограничение.

**Схемы разложены по статусам, и отсутствие схемы — тоже результат.** Если
сервер вернул статус, которого спецификация для этого эндпоинта не обещает
(B1: 200 вместо 201, B7: 200 вместо 204), сверять тело не с чем — проверка
сообщает `no-schema` и перечисляет ожидавшиеся статусы. Следствие, о котором
стоит помнить: B3 (`passwordHash`) схемой не ловится, потому что ответ `POST`
и так приходит с неописанным статусом 200 и до тела дело не доходит.

**`matchPath` экспортирован из `server.js` и переиспользуется проверкой.**
UI должен понять, что `/users/1` — это `GET /users/:id`; второй матчер в
клиенте означал бы два места, обязанные совпадать. Экспорт — единственная
правка в работающем роутере, тело функции не тронуто.

**Схемы компилируются один раз на загрузку модуля.** `ajv.compile()` генерирует
код валидатора и стоит заметно дороже самой проверки, а схемы — константы.
Побочный плюс: ошибка в схеме обнаружится при старте, а не при первом клике.

**Метод и путь отвеченного запроса хранятся отдельно** (`answered`). Студент
вправе поменять поле пути после отправки, и проверка обязана сверять ответ с
тем эндпоинтом, который реально спрашивали.

**Сообщения ajv не переводятся.** Они лаконичны и на английском — ровно такие,
какие студент увидит в настоящем проекте. Дополняется только
`additionalProperties`: ajv не называет лишнее поле в тексте, имя берётся из
`error.params.additionalProperty`.

**Мини-`expect` вместо chai.** Настоящий Postman использует chai; тянуть его
сюда ради десятка матчеров смысла нет — реализовано подмножество: `equal`,
`eql`, `a`/`an`, `property`, `lengthOf`, `include`, `above`, `below`, `oneOf`,
геттеры `null`, `true`, `false`, `undefined`, `exist`, `empty` и отрицание
`not`. Устройство стоит понимать: слова-связки (`to`, `be`, `have`, `is`, …) —
это геттеры, возвращающие тот же объект, они ничего не делают и нужны только
для читаемости. Проверку выполняет метод в конце цепочки, а `not` возвращает
новый объект с перевёрнутым флагом. Проверки без скобок (`.to.be.null`) —
геттеры, срабатывающие в момент чтения свойства; в chai ровно так же.

**Тест считается упавшим, если функция бросила исключение.** Никакого
отдельного механизма у тестов нет — это тот же принцип, что в Postman и chai.
Упавший тест не прерывает остальные, иначе первый провал скрыл бы весь отчёт.

**Падение всего скрипта и падение теста — разные вещи.** Синтаксическая ошибка
или исключение вне `pm.test` означают «тесты не запускались», а не «ноль
тестов прошло», и в UI это отдельная строка. Конструирование `new Function()`
и вызов стоят в одном `try`: `SyntaxError` вылетает уже на конструкторе.
Скрипт исполняется с `'use strict'`, чтобы забытый `var` не создавал
глобальную переменную.

**Тесты прогоняются автоматически после каждого ответа**, как в Postman, плюс
есть кнопка повторного прогона по тому же ответу — она нужна, когда скрипт
правят уже после получения ответа. Кнопка намеренно не отправляет запрос
заново: состояние сервера могло измениться, и тесты проверяли бы уже другой
ответ. Скрипт берётся тот, что был на момент отправки.

**Панель Tests ловит то, что не ловит проверка по схеме.** Показательный
случай — B3: схема до тела `POST /users` не добирается, потому что статус 200
спекой не описан, а `pm.expect(pm.response.json()).to.not.have.property(
'passwordHash')` находит лишнее поле сразу. Это и есть смысл двух инструментов
рядом.

**Сохраняется ввод, а не результаты работы сервера.** В снимок идут метод,
путь, тело, тестовый скрипт, история, репорты и открытые подсказки. Ответ,
результаты тестов и проверки по схеме не сохраняются сознательно: они относятся
к состоянию сервера, которого после перезагрузки уже нет — сервер поднимается
заново из `SEED_USERS`. Показать старый ответ рядом со свежим сервером значило
бы соврать.

**Снимок версионирован.** Поле `version` в сохранённом объекте сверяется при
чтении, и снимок другой версии игнорируется целиком. Это надёжнее попыток
угадать, какие поля старого формата ещё годятся; цена — потерянный прогресс
ровно в тот раз, когда формат поменялся.

Правило, когда поднимать версию, уточнено в v0.4. Изначально было записано
«при любом изменении набора полей», но добавление `variables` показало, что
это слишком грубо: каждое поле читается через `?? умолчание`, поэтому старый
снимок без нового поля читается корректно, а поднятие версии стёрло бы
работающий прогресс на ровном месте. Поэтому: **добавление необязательного
поля с умолчанием версию не поднимает; поднимает только несовместимое
изменение** — переименование поля, смена его типа или смысла.

**Обращение к `localStorage` целиком в `try/catch`, и это не перестраховка.**
Само чтение свойства бросает исключение в приватном режиме Safari и при
запрете хранилища в настройках браузера; `JSON.parse` бросает на испорченном
или чужом содержимом; `setItem` бросает при переполнении квоты. Любой из этих
случаев без обработки означал бы, что тренажёр не запускается вовсе. Есть и
четвёртая причина: серверный рендеринг компонентов идёт в Node, где `window`
нет, поэтому в `storage.js` стоит проверка `typeof window`.

**Запись отложена на 300 мс.** `localStorage` синхронный и блокирует поток, а
скрипт набирают посимвольно. Отмена предыдущего таймера сделана уборкой
эффекта — той функцией, которую `useEffect` возвращает: React вызывает её
перед следующим запуском эффекта, поэтому запись происходит один раз через
300 мс после последнего изменения.

**Счётчики id восстанавливаются из снимка.** `entryId` и `reportId` считаются
как максимум сохранённых id, иначе после перезагрузки новые записи получили бы
уже занятые номера, и React начал бы путать элементы списка: `key` обязан быть
уникальным.

**Кнопки «Сбросить состояние сервера» и «Начать заново» — разные вещи.**
Первая касается только данных сервера. Вторая стирает сохранённое: скрипт,
историю, найденные баги, подсказки, — и поэтому спрашивает подтверждение через
`window.confirm`. Скрипт пишут руками, случайная потеря обиднее всего.

**Подстановка `{{имя}}` идёт до разбора, а не после.** Тело
`{"id": {{userId}}}` невалидно как JSON и становится валидным только после
замены, поэтому `parseBody` получает уже подставленный текст. Подстановка
чисто текстовая, как в Postman: она ничего не знает ни про JSON, ни про URL.

**Неизвестная переменная не блокирует отправку.** `{{token}}`, которого нет в
таблице, уходит на сервер как есть — так поступает и Postman. Увидеть в ответе
собственный `{{token}}` полезнее, чем упереться в запрет; UI при этом
предупреждает заранее, перечисляя ненайденные имена.

**Переменные хранятся списком записей `{id, name, value}`, а не объектом.**
В объекте переименование ключа во время набора создавало бы по новому ключу на
каждую букву. `id` нужен как React key: строки удаляются из середины таблицы.
Счётчика в `useRef` здесь нет — `nextId(list)` выдаёт номер из самого списка
чистой функцией, поэтому её можно звать в том числе изнутри функции
обновления состояния, которая обязана оставаться чистой.

**Скрипт получает копию переменных, а не сам объект.** `runTests` возвращает
новый набор третьим полем результата, и App вливает его в список через
`mergeVariables`. Так изменения доходят наверх одним куском, а падение скрипта
на середине сохраняет только то, что он успел сделать до падения. Слияние
правит существующие строки на месте (порядок в таблице не прыгает), дописывает
новые в конец и убирает то, что скрипт снял через `unset`.

**Значения переменных всегда строки.** `pm.environment.set('id', 5)` кладёт
`"5"`: в таблице лежат строки, подстановка даёт строку, и `get` не должен
возвращать число там, где `{{id}}` подставит текст. В Postman так же.

**Цепочка — это не новый механизм, а связка уже готовых.** Скрипт сохраняет
значение из ответа, подстановка подставляет его в следующий запрос. Ничего
специально «цепочечного» в коде нет, и это правильно: в Postman так же.
Показательно, что цепочка ловит B6 — `PUT` отвечает новым именем, а
последующий `GET /users/{{userId}}` возвращает старое.

**У бага несколько допустимых типов, а не один.** Введено в v0.4.1 после
прохождения тренажёра целиком: `passwordHash` в ответе — одновременно утечка
и нарушение контракта, и отклонять второй ответ значило спорить со студентом,
который прав. Поэтому в каталоге `types: [...]`, а инвариант уникальности
проверяет все пары «эндпоинт × каждый тип».

**Эндпоинт `*` матчится с любым конкретным, но только если точной пары не
нашлось.** Порядок принципиален: `*` означает «во всех ответах», и проверяйся
он первым — перехватывал бы репорты по конкретным эндпоинтам. Причина, по
которой поиск по `*` вообще нужен: общий дефект студент видит в ответе
конкретного запроса и логично репортит именно туда. До правки B9 (дата не по
ISO) отклонялся везде, кроме явно выбранного пункта `*`, — это выглядело как
«ты не прав», хотя студент был прав.

**Тип `format` отделён от `contract`.** Пока формат даты был `contract`,
репорт «`GET /users/:id` + contract» был неотличим от «в теле не тот объект»,
и сверка выбирала не тот баг. Общий инвариант, который теперь проверяется:
тип бага с эндпоинтом `*` не должен принадлежать никакому другому багу.

**Отклонённый репорт сообщает, есть ли на этом эндпоинте что искать.**
Сухое «не совпало» заставляет усомниться в самом наблюдении, тогда как ошибка
чаще в выборе типа. Формулировка намеренно не льстит и не называет тип:
«ненайденные расхождения ещё есть, но не с этим типом дефекта».

**Задания — данные, как спека и каталог.** `users.tasks.js` перечисляет, что
сделать и что с чем сравнить, не называя дефект. Выполненность не хранится:
задание закрыто, когда засчитаны все связанные с ним баги, и это вычисляется
при рендере из уже существующего списка найденного — нового механизма
отслеживания не появилось. Инвариант: задание не может ссылаться на
несуществующий баг, иначе получилось бы задание, которое невозможно закрыть,
и по UI это было бы неотличимо от невыполненного.

**Поле `tool` в задании называет инструмент.** Без него студент не догадается,
что панель Tests и переменные нужны не для красоты: B4 и B6 без них не
находятся в принципе.

**Значок вместо цветного текста.** Статусы, методы, вердикты репортов,
PASS/FAIL и бейджи заданий устроены одинаково: цвет текста плюс подложка того
же цвета с прозрачностью 16%. Подложки задаются через `color-mix` от самого
цвета, поэтому смена акцента в `:root` меняет и подложки. Браузер без
поддержки `color-mix` просто отбросит эти свойства: значки останутся цветным
текстом без фона, а не сломаются.

**Заголовки панелей липкие.** Колонки прокручиваются независимо и бывают
длинными; без этого непонятно, к какой секции относится то, что сейчас на
экране. Отрицательные горизонтальные поля растягивают подложку заголовка на
всю ширину колонки поверх её внутренних отступов — иначе содержимое проезжало
бы в зазорах по краям.

**Один класс `.btn` вместо шести наборов правил.** До v0.4.2 кнопки в панелях
request, report, hints, schema, tests и env имели свои почти одинаковые
правила. Различаются они только весом, поэтому остались `.btn`, `.btn--primary`
(главное действие панели: «Отправить», «Завести баг») и `.btn--small`.

**`statusClass` вынесен в `src/status.js`** — долг, висевший с v0.1, закрыт в
v0.4.2, когда правка стилей всё равно затронула все три файла с копиями. Копии
успели разойтись: 3xx не учитывался нигде и попадал в зелёную группу вместе
с 2xx.

**Инструменты задания — идентификаторы, а не готовый текст.** `tools: ['chain',
'tests']` вместо строки «переменные + цепочка запросов»: по идентификатору
раскрашивается бейдж, подписи лежат в `TASK_TOOLS` рядом с заданиями.
Инвариант заданий заодно проверяет, что инструмент известен.

**Сворачивание разделов вынесено в один компонент `Section`.** До этого
справка сворачивалась своей кнопкой со своими стилями, а остальные разделы не
сворачивались вовсе. Заголовок раздела — кнопка целиком, а не стрелка: попасть
мышью в строку легче. Открытость хранится в App и попадает в снимок
localStorage, поэтому свёрнутое остаётся свёрнутым после перезагрузки.
Добавить сворачивание любому другому разделу теперь — одна обёртка.

**Свёрнутый раздел показывает сводку.** У заданий это «2 / 8», у спецификации
число эндпоинтов, у истории и переменных — их количество, у Tests — результат
последнего прогона. Свернув панель, студент не должен терять из виду то, ради
чего он её открывал. Сводка не показывается, когда считать нечего: «0 запросов»
в заголовке пустой истории — шум, а не информация.

**Сворачиваются все шесть разделов**: справка, задания, спецификация,
переменные, Tests и история. По умолчанию открыты все — состояние по первому
входу не должно ничего прятать. Правая колонка (ответ, результаты, проверка,
баг-репорт, прогресс) не сворачивается: там всё появляется по ходу работы и
исчезает само.

**Русские числительные вынесены в `src/plural.js`.** Форм три, и выбор зависит
от двух последних цифр, а не от последней: «21 запрос», но «11 запросов».
Первая копия правила появилась в списке заданий, вторая понадобилась для
сводок — вынесена сразу, до третьей.

**Ширину колонок задаёт пользователь, доли хранятся в состоянии.**
`grid-template-columns` собирается инлайновым стилем из массива долей, а
разделители — настоящие элементы сетки, а не `gap`: тянуть промежуток нельзя.
Соседние колонки при перетаскивании обмениваются шириной, сумма долей
постоянна — иначе поехала бы вся сетка. Упор в минимальную ширину (200 px)
не схлопывает панель, а просто игнорирует движение.

**Пересчёт долей вынесен в `src/columns.js`.** Из браузера нужна только
фактическая ширина сетки в пикселях, она передаётся аргументом, — поэтому
логику видно целиком и её можно прогнать в Node, как `bug-check` и
`variables`. `resizeColumns` возвращает `null`, когда двигать некуда: так
вызывающий код не трогает состояние зря.

**Сохранённые доли проверяются при чтении.** Снимок лежит в localStorage,
его можно испортить руками или оставить от прежней версии; кривые доли
сделали бы раскладку неработающей, а починить её через интерфейс было бы уже
нельзя. `sanitizeColumns` откатывается к умолчанию на всём, что не массив из
трёх конечных чисел.

**Разделитель использует pointer events и `setPointerCapture`.** Захват
привязывает последующие события указателя к разделителю, даже когда курсор
ушёл на соседнюю панель; без него пришлось бы вешать обработчики на `window`
и снимать их вручную. Точка отсчёта сдвигается на каждом шаге, а не хранится
от начала перетаскивания: иначе упор в минимум копил бы «долг», и колонка не
двинулась бы обратно, пока курсор не вернётся в исходную точку. Двойной клик
возвращает умолчание, стрелки влево-вправо двигают границу с клавиатуры.

**Вводная справка отвечает на «что это вообще такое», а не только «куда
нажимать».** Читатель — QA-инженер, который знает REST и умеет писать
баг-репорты, но про этот тренажёр не знает ничего. Поэтому в тексте явно
сказано: сервер поддельный и работает в той же вкладке, сети нет; дефектов
десять и они вшиты намеренно; отличие от Postman в том, что здесь известен
правильный ответ. Отдельный раздел — что происходит с данными: `POST`, `PUT`
и `DELETE` по-настоящему меняют состояние сервера, перезагрузка его
сбрасывает, а прогресс и скрипт переживают.

**Справка по разделам — данные в `src/reference.js`.** Строка справки это
пара «что написать» и «что произойдёт». Держать тексты в одном файле, а не в
шести компонентах, нужно ровно затем, чтобы они не разошлись с поведением:
проверить справку целиком можно, открыв один файл. Типы дефектов в справке
баг-репорта не переписаны заново, а взяты из `BUG_TYPES` — иначе описание
разошлось бы с тем, что студент выбирает в форме.

**Открытость справки не сохраняется, в отличие от свёрнутости раздела.**
Свёрнутый раздел — это выбранная раскладка, она переживает перезагрузку.
Справка — сиюминутный взгляд в шпаргалку, и оставлять её открытой навсегда
незачем. Поэтому её состояние живёт в `useState` внутри `Section`, а не в App.

**Справка открывается и у свёрнутого раздела.** Заглянуть в список матчеров,
не разворачивая редактор скрипта, — обычное дело.

**`Section` без `onToggle` не сворачивается.** Так устроены разделы правой
колонки: там содержимое появляется по ходу работы и исчезает само, прятать
нечего, а единый заголовок со справкой нужен и им.

**Каждое отступление от спецификации помечено в коде идентификатором бага** —
`// B1`, `// B5` и так далее, прямо в точке дефекта. Комментарии на русском.

**`App.jsx` — единственный владелец состояния**, компоненты получают всё через
props и сообщают наверх колбэками. Это нужно для истории запросов: клик по
элементу истории должен перезаписывать поля конструктора извне.

**Производные значения не хранятся в состоянии.** Разобранный путь
(`splitPath`) и разобранное тело (`parseBody`) вычисляются при рендере из
`path` и `bodyText`. Дублировать их в `useState` — источник рассинхрона.

**История хранит сырой ввод, а не разобранный.** В записи лежат `path` и
`bodyText` ровно в том виде, в каком их набрали. Иначе `/users?limit=0`
вернулось бы в поле как `/users` с потерянным query, и восстановление по клику
работало бы наполовину.

**Обновление истории — функциональной формой:**
`setHistory((current) => [entry, ...current])`. Запись добавляется внутри
`setTimeout`, где переменная `history` — захваченный снимок на момент отправки.
При двух быстрых запросах подряд форма со значением затёрла бы первую запись.

**Счётчик id элементов истории — в `useRef`, а не в `useState`.** Значение
должно переживать перерисовки, но его изменение само по себе перерисовку не
требует: список обновляется рядом и вызовет её сам. Менять `.current` во время
рендера нельзя, только в обработчиках.

**Сброс не трогает историю и последний ответ.** Они описывают то, что уже
произошло; сброс касается только данных сервера. Время сброса печатается рядом
с кнопкой, иначе нажатие выглядит как «ничего не случилось».

## Чем какой баг находится

Проверено прохождением всего тренажёра (v0.4.1). Инструменты не дублируют
друг друга — это важно, иначе часть функционала оказалась бы мёртвой.

| Как находится | Баги |
|---|---|
| Только глазами, сравнением со спекой | B5 |
| Проверкой по схеме | B8, B9, B10 |
| Схема даёт только «статус не описан» | B1, B7 |
| Только тестом или цепочкой запросов | B2, B3, B4, B6 |

B6 находится **только** цепочкой `PUT` → `GET` по переменной, B4 — только
удалением с последующим перечитыванием списка.

## Вшитые баги v0.1

| id | Где | Дефект |
|---|---|---|
| B1 | POST /users | 200 вместо 201 |
| B2 | POST /users | email не валидируется, `abc` без `@` принимается |
| B3 | POST /users | в ответе лишнее поле `passwordHash` |
| B4 | GET /users | `total` всегда 100, не связан с реальным количеством |
| B5 | GET /users?limit=0 | весь список вместо 400 |
| B6 | PUT /users/:id | `name` молча не обновляется, ответ 200 со старым значением |
| B7 | DELETE /users/:id | 200 с телом вместо 204 без тела |
| B8 | GET /users/:id | несуществующий id → 200 и тело `null` вместо 404 |
| B9 | везде | `createdAt` без `T` и таймзоны, не ISO 8601 |
| B10 | GET /users | в элементах списка нет поля `role` |

Корректно и намеренно не сломано: `limit=101` → 400, дубликат email → 409,
отсутствие обязательного поля → 400, `PUT`/`DELETE` по несуществующему id →
404. Это важно: если сломано всё, тренажёр теряет смысл. B5 находится именно
потому, что верхняя граница диапазона проверена, а нижняя нет.

## Известный долг

- **`new Function()` — это не песочница.** Скрипт из панели Tests выполняется
  в том же контексте, что и приложение: ему доступны `window`, `document` и
  всё остальное. Для локального тренажёра, где студент пишет скрипт сам себе,
  это приемлемо, но `while (true)` повесит вкладку без возможности прервать.
  Настоящий Postman исполняет скрипты в изолированной среде. Правильное
  решение — Web Worker с таймаутом: в него нужно передавать только ответ,
  больше скрипту ничего не нужно. Отложено сознательно.
- **Подсказка про «промах рядом» в начале прохождения срабатывает почти
  всегда.** Она честная — на эндпоинте действительно есть ненайденное
  расхождение, — но пока не найдено ничего, это верно почти для любого
  эндпоинта, и сигнал слабый. Ближе к концу прохождения становится полезной.
  Как сделать лучше, непонятно: система не знает, что именно студент имел в
  виду. Оставлено как есть.
- **Состояние mock-сервера не сохраняется.** Созданные и удалённые
  пользователи после перезагрузки возвращаются к `SEED_USERS`. Сделано
  намеренно: сохранённый ответ рядом со свежим сервером вводил бы в
  заблуждение. Для v0.4 (цепочки запросов) это стоит пересмотреть — там
  результат одного запроса используется в следующем.

## Тесты

```
npm test
```

93 теста на встроенном раннере Node (`node --test`), без единой новой
зависимости: в Node 22 есть и раннер, и `node:assert`. Vitest не ставился
сознательно — компоненты всё равно проверяются серверным рендерингом, а для
чистых модулей встроенного хватает.

**Запускать надо шаблоном, а не каталогом:** `node --test "tests/*.test.js"`.
Форма `node --test tests/` на этой машине падает с `MODULE_NOT_FOUND` —
каталог принимается за модуль. Кавычки обязательны: раскрывать шаблон должен
Node, а не оболочка.

Тесты идут в том же workflow перед сборкой, поэтому сломанный код не уезжает
на сайт. Уже опубликованная версия при этом не откатывается — она просто
остаётся висеть, а в Actions появляется красный крестик.

### Что покрыто

| Файл | О чём |
|---|---|
| `expect.test.js` | каждый матчер с обеих сторон и с `not` |
| `bug-check.test.js` | сверка репортов, приоритет точного совпадения над `*` |
| `pm-runtime.test.js` | объект `pm`, отличие упавшего теста от упавшего скрипта |
| `schema-check.test.js` | вердикты проверки по схеме на живом mock-сервере |
| `server.test.js` | корректное поведение и все десять вшитых дефектов |
| `catalog.test.js` | согласованность каталога, заданий, схем и спецификации |
| `misc.test.js` | ширины колонок, числительные, группы статусов |

### Принципиальные решения по тестам

**Каждый матчер `expect` проверяется с обеих сторон.** Односторонняя проверка
здесь бесполезна: матчер, который не бросает никогда, пройдёт её целиком. Это
худший вид поломки в тренажёре — тесты студента становятся вечнозелёными и
молчат о настоящих дефектах. По той же причине у каждого матчера отдельно
проверяется `not`: ошибка во флаге отрицания даёт тот же результат.

**Вшитые дефекты закреплены тестами.** Выглядит непривычно — тесты требуют,
чтобы сервер вёл себя неправильно, — но неправильное поведение здесь и есть
содержание. Если B6 однажды «починится» при правке соседнего кода, задание
перестанет решаться, а заметить это иначе нечем. Каждый такой тест назван по
идентификатору дефекта. Проверено мутацией: добавление `name` в набор
изменений `PUT` роняет тест B6.

**Инварианты содержимого вынесены в отдельный файл.** `catalog.test.js` ловит
не поломку кода, а рассогласование данных: задание, ссылающееся на
несуществующий баг; дефект, недостижимый через форму; эндпоинт спецификации
без схемы. Всё это иначе проявляется как тихо неработающая функция.

**Тесты сверки используют свой маленький каталог**, а не вшитые дефекты
сценария Users: проверяется логика сопоставления, и она не должна ломаться от
добавления одиннадцатого бага.

**Набор проверен мутациями.** Сломанное отрицание в `expect` роняет 10 тестов,
перестановка приоритета `exact ?? wide` в сверке — 1, «починка» B6 — 1. Тест,
который не краснеет при внесении ошибки, не тест.

### На будущее

Файл спецификации назван `users.contract.js`, а не `users.spec.js`, потому что
суффикс `.spec.js` тест-раннеры подхватывают как тестовый файл. Сейчас это
особенно важно: `npm test` берёт всё по шаблону.
