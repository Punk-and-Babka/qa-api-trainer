# QA API Trainer

Веб-тренажёр для обучения QA тестированию API. Ключевая идея:
**эталонная спецификация + намеренно сломанный fake-сервер + клиент запросов**.
Отличие от Postman в том, что здесь есть «правильный ответ»: спека известна,
баги вшиты списком, поэтому тренажёр может проверять, нашёл ли студент
расхождение.

Это **не** клон интерфейса Postman. Интерфейс минимальный, вся ценность в
контенте — в багах и заданиях.

## Текущее состояние

**v0.1, v0.2 и v0.3 закрыты.** Работает: спецификация в левой панели, конструктор
запроса, отправка в mock-сервер, просмотр ответа с подсветкой JSON, история
запросов с восстановлением по клику, кнопка сброса состояния сервера, форма
баг-репорта со сверкой по каталогу, счётчик «найдено N из 10», лента репортов
с вердиктами, подсказки по одной, проверка ответа по JSON Schema через ajv и
панель Tests с объектом `pm` и своим мини-`expect`.

Осознанно отсутствует: переменные окружения,
сохранение прогресса между перезагрузками страницы. Всё это — следующие
версии, см. роадмап ниже.

Следующий шаг: **v0.4 — цепочки запросов и переменные окружения**.

Ветка `main`, удалённого репозитория нет — всё локально.

## Стек и жёсткие ограничения

- React + Vite, **чистый JavaScript, не TypeScript**.
- Обычный CSS. Без Tailwind, без UI-китов, без Material UI.
- Состояние — `useState`/`useReducer`. Без Redux, Zustand, react-query.
- Роутинга нет и на v0.1 не нужен.
- Зависимости проекта: `react`, `react-dom`, `vite`, `@vitejs/plugin-react`,
  `ajv` и `ajv-formats`. Подсветка JSON написана вручную
  (`src/components/JsonView.jsx`) вместо внешней библиотеки.
  `ajv` добавлен в v0.3a осознанно: полноценный валидатор JSON Schema — это не
  «полсотни строк своего кода», а самописное подмножество учило бы
  почти-стандарту. `ajv-formats` обязателен в нагрузку — без него ключевое
  слово `format` молча игнорируется. Цена: бандл вырос с 76 до 116 КБ gzip.
- **Любая новая npm-зависимость сначала предлагается и обосновывается, и
  ставится только после явного согласия.**

## Запуск

```
npm install
npm run dev
```

Открывается `http://127.0.0.1:5173/`.

**Важно: в `vite.config.js` намеренно прописан `host: '127.0.0.1'`.** По
умолчанию Vite слушает имя `localhost`, а Node начиная с 17 версии не сортирует
результаты резолва — на этой машине первым идёт `::1`. При этом IPv6-петля
здесь не работает (`ping ::1` даёт 100% потерь: VPN-клиент с TUN-адаптером
перехватывает IPv6-маршрут). Симптом был обманчивый: сервер поднимался и писал
«ready», но страница в браузере не открывалась. Эту строку не удалять.

Смежное: `netstat -p tcp` на Windows показывает **только IPv4**. Чтобы увидеть
IPv6-сокеты, нужен `netstat -p tcpv6` — иначе легко решить, что сервер вообще
не слушает.

### Контракт mock-сервера

```js
// вход
{ method, path: "/users/1", query: { limit: "10" }, headers, body }
// выход
{ status: 200, headers: {...}, body: {...}, time: 43 }
```

`handle()` — **синхронная функция**. Задержку ответа изображает `setTimeout` в
`App.jsx` на то число миллисекунд, которое вернул сам сервер. Внутрь роутера
задержку не вносить: он должен оставаться вызываемым из проверки одной строкой
без `await`.

Неизвестный путь → 404 с телом `{ "error": "Not found" }`.

### Принципиальные решения

**Состояние сервера живёт в модуле, а не в React.** Fake-сервер обязан
переживать перерисовки компонентов. `resetState()` копирует каждую запись
из `SEED_USERS` через spread — иначе обработчики мутировали бы эталон и сброс
перестал бы работать.

**Спека и каталог багов — это данные.** `SpecPanel` обходит объект контракта и
не знает про конкретный сценарий: новый эндпоинт добавляется правкой одного
`users.contract.js`. То же для багов — в v0.2 `users.bugs.js` станет эталоном
для проверки баг-репортов.

**Само дефектное поведение остаётся кодом.** Декларативного движка, который
«портит» корректный ответ на лету, сознательно нет: часть багов (B6 — поле
молча не сохраняется, B8 — 200 с телом null) невыразима декларативно без языка
правил, который окажется больше всего сервера. Вернуться к этому решению можно
в v0.5, когда багов станет много.

**Баг опознаётся по паре «эндпоинт + тип дефекта», и уникальность пары —
явный инвариант каталога.** Свободный текст описания сверяется человеком, а не
машиной: он показывается рядом с эталонной формулировкой, но на счётчик не
влияет. Альтернативы (ручная отметка «совпало» студентом, подтверждение эталона
после автосверки) обсуждались и отклонены: счётчик должен что-то доказывать, а
не накручиваться. Слабое место такой сверки — она ломается молча, если два бага
дадут одну пару, поэтому `users.bugs.js` при импорте вызывает
`assertUniquePairs()` и падает с указанием конфликтующих id. Раньше уникальность
пар была случайным свойством данных, теперь это проверяемое требование.

**Логика сверки вынесена из React в `src/bug-check.js`.** `checkReport()`,
`endpointOptions()` и `foundBugIds()` — чистые функции над массивами: их видно
целиком, их можно прогнать из Node одной строкой и позже покрыть тестами, не
поднимая браузер.

**Список эндпоинтов для формы считается из контракта**, а не пишется руками:
новый эндпоинт появляется в спеке и в выпадающем поле одновременно. Пункт `*`
дописывается отдельно — он не эндпоинт, а способ сообщить о дефекте во всех
ответах сразу (B9, формат даты).

**Черновик формы баг-репорта живёт в самом компоненте** — сознательное
отступление от правила «App владеет всем». Правило появилось ради истории
запросов, где клик по элементу обязан перезаписать поля извне. Черновику это не
нужно: снаружи его никто не задаёт и не читает, наверх уходит только готовый
репорт. Поднимать такое состояние — четыре лишних props без выигрыша.

**Вердикт репорта считается в обработчике, а не внутри `setReports`.** Здесь,
в отличие от истории, обработчик выполняется синхронно по клику, и `reports` в
нём актуален — устаревшего снимка, из-за которого истории понадобилась
функциональная форма, не возникает. Внутрь updater'а нельзя класть и счётчик
`reportId`: React вправе вызвать функцию обновления дважды, она обязана быть
чистой. Сам append при этом всё равно сделан функциональной формой.

**Найденные баги не хранятся состоянием** — `foundBugIds(reports)` считается
при рендере из ленты репортов. Тот же принцип, что и с разобранным путём.

**Подсказки открываются по одной и только для ненайденных багов**, в порядке
каталога. Число открытых подсказок показано рядом со счётчиком: это честная
оценка результата, а не наказание — засчитывание от подсказки не зависит.

**Сброс состояния сервера не трогает прогресс.** Он касается только данных
сервера; найденные баги и лента репортов — результат работы студента.

**Схемы пишутся по спецификации, а не по фактическому поведению.** Иначе
проверка подтверждала бы баги вместо того, чтобы их ловить. Побочный эффект
намеренный: `additionalProperties: false` ловит `passwordHash` (B3),
`format: date-time` — дату без `T` (B9), `required` — отсутствие `role` в
списке (B10), а `type: object` — тело `null` вместо 404 (B8). Поэтому проверка
запускается кнопкой, а не автоматически: сначала студент смотрит глазами,
потом сверяется машиной. Это методический выбор, а не техническое ограничение.

**Схемы разложены по статусам, и отсутствие схемы — тоже результат.** Если
сервер вернул статус, которого спецификация для этого эндпоинта не обещает
(B1: 200 вместо 201, B7: 200 вместо 204), сверять тело не с чем — проверка
сообщает `no-schema` и перечисляет ожидавшиеся статусы. Следствие, о котором
стоит помнить: B3 (`passwordHash`) схемой не ловится, потому что ответ `POST`
и так приходит с неописанным статусом 200 и до тела дело не доходит.

**`matchPath` экспортирован из `server.js` и переиспользуется проверкой.**
UI должен понять, что `/users/1` — это `GET /users/:id`; второй матчер в
клиенте означал бы два места, обязанные совпадать. Экспорт — единственная
правка в работающем роутере, тело функции не тронуто.

**Схемы компилируются один раз на загрузку модуля.** `ajv.compile()` генерирует
код валидатора и стоит заметно дороже самой проверки, а схемы — константы.
Побочный плюс: ошибка в схеме обнаружится при старте, а не при первом клике.

**Метод и путь отвеченного запроса хранятся отдельно** (`answered`). Студент
вправе поменять поле пути после отправки, и проверка обязана сверять ответ с
тем эндпоинтом, который реально спрашивали.

**Сообщения ajv не переводятся.** Они лаконичны и на английском — ровно такие,
какие студент увидит в настоящем проекте. Дополняется только
`additionalProperties`: ajv не называет лишнее поле в тексте, имя берётся из
`error.params.additionalProperty`.

**Мини-`expect` вместо chai.** Настоящий Postman использует chai; тянуть его
сюда ради десятка матчеров смысла нет — реализовано подмножество: `equal`,
`eql`, `a`/`an`, `property`, `lengthOf`, `include`, `above`, `below`, `oneOf`,
геттеры `null`, `true`, `false`, `undefined`, `exist`, `empty` и отрицание
`not`. Устройство стоит понимать: слова-связки (`to`, `be`, `have`, `is`, …) —
это геттеры, возвращающие тот же объект, они ничего не делают и нужны только
для читаемости. Проверку выполняет метод в конце цепочки, а `not` возвращает
новый объект с перевёрнутым флагом. Проверки без скобок (`.to.be.null`) —
геттеры, срабатывающие в момент чтения свойства; в chai ровно так же.

**Тест считается упавшим, если функция бросила исключение.** Никакого
отдельного механизма у тестов нет — это тот же принцип, что в Postman и chai.
Упавший тест не прерывает остальные, иначе первый провал скрыл бы весь отчёт.

**Падение всего скрипта и падение теста — разные вещи.** Синтаксическая ошибка
или исключение вне `pm.test` означают «тесты не запускались», а не «ноль
тестов прошло», и в UI это отдельная строка. Конструирование `new Function()`
и вызов стоят в одном `try`: `SyntaxError` вылетает уже на конструкторе.
Скрипт исполняется с `'use strict'`, чтобы забытый `var` не создавал
глобальную переменную.

**Тесты прогоняются автоматически после каждого ответа**, как в Postman, плюс
есть кнопка повторного прогона по тому же ответу — она нужна, когда скрипт
правят уже после получения ответа. Кнопка намеренно не отправляет запрос
заново: состояние сервера могло измениться, и тесты проверяли бы уже другой
ответ. Скрипт берётся тот, что был на момент отправки.

**Панель Tests ловит то, что не ловит проверка по схеме.** Показательный
случай — B3: схема до тела `POST /users` не добирается, потому что статус 200
спекой не описан, а `pm.expect(pm.response.json()).to.not.have.property(
'passwordHash')` находит лишнее поле сразу. Это и есть смысл двух инструментов
рядом.

**Каждое отступление от спецификации помечено в коде идентификатором бага** —
`// B1`, `// B5` и так далее, прямо в точке дефекта. Комментарии на русском.

**`App.jsx` — единственный владелец состояния**, компоненты получают всё через
props и сообщают наверх колбэками. Это нужно для истории запросов: клик по
элементу истории должен перезаписывать поля конструктора извне.

**Производные значения не хранятся в состоянии.** Разобранный путь
(`splitPath`) и разобранное тело (`parseBody`) вычисляются при рендере из
`path` и `bodyText`. Дублировать их в `useState` — источник рассинхрона.

**История хранит сырой ввод, а не разобранный.** В записи лежат `path` и
`bodyText` ровно в том виде, в каком их набрали. Иначе `/users?limit=0`
вернулось бы в поле как `/users` с потерянным query, и восстановление по клику
работало бы наполовину.

**Обновление истории — функциональной формой:**
`setHistory((current) => [entry, ...current])`. Запись добавляется внутри
`setTimeout`, где переменная `history` — захваченный снимок на момент отправки.
При двух быстрых запросах подряд форма со значением затёрла бы первую запись.

**Счётчик id элементов истории — в `useRef`, а не в `useState`.** Значение
должно переживать перерисовки, но его изменение само по себе перерисовку не
требует: список обновляется рядом и вызовет её сам. Менять `.current` во время
рендера нельзя, только в обработчиках.

**Сброс не трогает историю и последний ответ.** Они описывают то, что уже
произошло; сброс касается только данных сервера. Время сброса печатается рядом
с кнопкой, иначе нажатие выглядит как «ничего не случилось».

## Вшитые баги v0.1

| id | Где | Дефект |
|---|---|---|
| B1 | POST /users | 200 вместо 201 |
| B2 | POST /users | email не валидируется, `abc` без `@` принимается |
| B3 | POST /users | в ответе лишнее поле `passwordHash` |
| B4 | GET /users | `total` всегда 100, не связан с реальным количеством |
| B5 | GET /users?limit=0 | весь список вместо 400 |
| B6 | PUT /users/:id | `name` молча не обновляется, ответ 200 со старым значением |
| B7 | DELETE /users/:id | 200 с телом вместо 204 без тела |
| B8 | GET /users/:id | несуществующий id → 200 и тело `null` вместо 404 |
| B9 | везде | `createdAt` без `T` и таймзоны, не ISO 8601 |
| B10 | GET /users | в элементах списка нет поля `role` |

Корректно и намеренно не сломано: `limit=101` → 400, дубликат email → 409,
отсутствие обязательного поля → 400, `PUT`/`DELETE` по несуществующему id →
404. Это важно: если сломано всё, тренажёр теряет смысл. B5 находится именно
потому, что верхняя граница диапазона проверена, а нижняя нет.

## Известный долг

- **`new Function()` — это не песочница.** Скрипт из панели Tests выполняется
  в том же контексте, что и приложение: ему доступны `window`, `document` и
  всё остальное. Для локального тренажёра, где студент пишет скрипт сам себе,
  это приемлемо, но `while (true)` повесит вкладку без возможности прервать.
  Настоящий Postman исполняет скрипты в изолированной среде. Правильное
  решение — Web Worker с таймаутом: в него нужно передавать только ответ,
  больше скрипту ничего не нужно. Отложено сознательно.
- **Прогресс и тестовый скрипт не переживают перезагрузку страницы.** Найденные баги и лента
  репортов и текст скрипта лежат в `useState` и теряются по F5. Для тренировки
  в один заход это терпимо, но перед режимом экзамена (v0.5) понадобится
  `localStorage`. Скрипт обиднее всего: его пишут руками.
- **`statusClass` существует в трёх копиях** — в `SpecPanel.jsx`,
  `ResponseViewer.jsx` и `HistoryList.jsx`. Просится в общий модуль
  `src/status.js` вместе с таблицей расшифровок `STATUS_TEXT`. Не вынесено
  потому, что это правка работающих файлов, а рефакторинг без просьбы запрещён.
  Предложено, решение за Антоном.
- **Резервной копии нет.** Репозиторий только локальный, на `D:`, без remote.
  Отказ диска уничтожит всё. Предложено завести приватный репозиторий на
  GitHub — ответа пока не было.

## Roadmap

- **v0.2 — сделана.** Форма баг-репорта, сверка со списком `bugs` по паре
  «эндпоинт + тип», счётчик, вердикты `accepted` / `duplicate` / `rejected`,
  подсказки. Открытый вопрос о способе засчитывания закрыт в пользу пары с
  инвариантом уникальности — обоснование выше, в принципиальных решениях.
- **v0.3a — сделана.** Валидация ответа по JSON Schema через `ajv` +

## Тесты

Автотестов пока нет намеренно — структура ещё не устоялась. Появятся позже,
и первые кандидаты — `src/bug-check.js`, `src/expect.js` и `src/pm-runtime.js`:
чистые функции без React. У `expect.js` проверять надо обе стороны каждого
матчера — и срабатывание, и несрабатывание с `not`; ошибка в флаге отрицания
даёт молча всегда проходящий тест, что хуже, чем падающий.

Проверка делается прогоном логики через Node и серверным рендерингом
компонентов. Второе неочевидно: Node не понимает JSX, а esbuild-бинарника в
`node_modules/.bin` нет (Vite 8 использует rolldown). Рабочий способ — собрать
временный входной файл SSR-сборкой Vite и запустить результат:

```
npx vite build --ssr smoke-render.jsx --outDir ./.smoke --logLevel error
node ./.smoke/smoke-render.js
```

Каталог сборки должен лежать **внутри проекта**: `react` и `react-dom`
остаются внешними импортами, и из временного каталога вне проекта Node их не
находит. И при поиске подстрок в разметке помнить про экранирование —
`renderToStaticMarkup` превращает кавычки в `&quot;`.

Когда тесты появятся, учесть: файл спецификации назван `users.contract.js`, а
не `users.spec.js`, потому что суффикс `.spec.js` тест-раннеры (Vitest, Jest)
подхватывают как тестовый файл.
